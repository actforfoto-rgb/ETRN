# ЭТрН: целевая архитектура пакетной подписи без физического Рутокена

Дата решения: 18.09.2026  
Статус: DEVELOPMENT / NO-DRIVER LAB  
Ветка: `dev/no-driver-lab-r1`

## Решение

Основной маршрут разработки:

```
Saby
  -> СБИС.ПодготовитьДействие для каждой ЭТрН
  -> точный подписываемый файл/хэш + AttachmentID
  -> пакетирование документов для Госключа
  -> Госключ / API ЕПГУ, УКЭП ИП
  -> получение отсоединённых подписей
  -> проверка и точное сопоставление document + attachment + hash
  -> СБИС.ВыполнитьДействие для каждой исходной ЭТрН
  -> повторное чтение каждой ЭТрН и подтверждение результата
```

Физический Рутокен водителя в целевой схеме отсутствует.

## Почему больше не строим решение на одном sabyCryptoOperation.Create для разных ЭТрН

Разбор Saby TMS 26.3246.5 дал согласованную модель:

- `CryptographyApi.createSigns(objectId, fileHashes, signType, ...)` принимает один `objectId` и список файлов.
- `CertificateOperation` содержит один `objectId` и список `signedFiles`.
- `SigningOperationFileInfo` содержит `fileId`, статус и ошибку, но не содержит отдельного `objectId/DocumentID` для каждого файла.
- публичная форма `sabyCryptoOperation.Create` также имеет один `DocumentID` и массив `Files[].AttachmentID`.

Это не является математическим доказательством того, что сервер обязательно отвергнет AttachmentID чужого документа, но клиентский и публичный контракт структурно ориентированы на один объект/документ. Для production-решения такой неописанный cross-document режим использовать нельзя.

R2 FIX2 сохраняется как исследовательское свидетельство, но не является основой продукта.

## Почему внешний маршрут подписи совместим с Saby

Saby документирует сценарий, в котором после `СБИС.ПодготовитьДействие` подпись создаётся внешним средством, а затем передаётся в `СБИС.ВыполнитьДействие`.

Для каждого подписанного вложения необходимо сохранить привязку:

```
DocumentID / RevisionID
StageID
Action
AttachmentID
hash подписанного содержимого
detached signature bytes
```

При выполнении действия подпись передаётся в соответствующее вложение как Base64 в структуре `Подпись.Файл.ДвоичныеДанные`. После вызова обязательно повторное чтение документа; HTTP 200 сам по себе не считается успешным завершением ЭТрН.

## Госключ для ИП

Рабочий кандидат для УКЭП организации/ИП в API ЕПГУ — профиль `60025907` («Подписание документов УКЭП юридическими лицами»).

По текущей реализации опубликованной спецификации/XSD:

- российский получатель может быть организацией или ИП;
- используется ОГРН/ОГРНИП и один идентификатор физического пользователя: СНИЛС или OID ЕСИА;
- ОГРНИП из 15 цифр проходит форму OGRN контракта;
- лимит одного задания — 20 бизнес-документов;
- поэтому 50 ЭТрН планируются как 20 + 20 + 10.

Лимит 20 и wire-contract считаются лабораторным Gate до проверки на официальном тестовом контуре API ЕПГУ.

## Что уже реализовано без сети

### ExternalSigningBatch

- детерминированная привязка `document + attachment + hash`;
- пакетирование с заданным лимитом;
- порядок возвращённых подписей не используется как идентификатор;
- missing / extra / duplicate signatures блокируют обработку;
- mismatch хэша блокирует обработку.

### GoskeyIpPackagePlan

- service code `60025907`;
- лимит 20;
- ОГРНИП строго 15 цифр;
- ровно один идентификатор пользователя: СНИЛС или OID;
- 50 документов -> 20 + 20 + 10.

Это модель контракта, а не сетевой клиент Госключа.

### SabyExecuteActionPayload

- подпись прикрепляется только к своему AttachmentID;
- используется точная RevisionID при наличии;
- сохраняются StageID и Action;
- документ и сертификат повторно не пересылаются;
- detached signature кодируется Base64;
- дубликаты AttachmentID блокируются.

## Что нужно для реальной интеграции Госключа

Нужен не аккаунт водителя и не его Рутокен, а зарегистрированная информационная система, имеющая право работать с API ЕПГУ/Госключа.

Минимальный внешний Gate:

1. зарегистрировать/использовать ИС для API ЕПГУ;
2. получить полномочие Госключа для отправки документов на подпись;
3. получить API Key / необходимые ESIA credentials;
4. получить доступ к тестовой среде;
5. определить сертификат/СКЗИ, которым наша ИС подписывает транспортный пакет `req.xml` и документы перед отправкой;
6. подтвердить serviceCode `60025907`, namespace и XSD на официальном стенде;
7. отправить полностью синтетический пакет без ЭТрН и без водительских данных;
8. проверить создание задания, статус и возврат подписанного результата;
9. только после этого подключать адаптер к Saby Prepare/ExecuteAction;
10. водительская приёмка — последняя стадия, не средство отладки.

## Production gates

Релиз водителю запрещён, пока не выполнены все условия:

- официальный тестовый контур `60025907` подтверждён;
- пакет из нескольких документов реально появляется в одном задании Госключа;
- полученные подписи можно однозначно сопоставить исходным файлам;
- УКЭП каждой подписи проверяется криптографически до передачи в Saby;
- durable store переживает убийство Android/backend процесса;
- Create/submit не повторяется после неопределённого результата;
- ExecuteAction имеет recovery/readback;
- 2, 20 и 50 синтетических ЭТрН проходят весь координатор;
- после этого отдельная ограниченная приёмка владельцем реальной УКЭП.

## Что не делаем

- не копируем закрытый ключ с Рутокена;
- не эмулируем Рутокен другим Android-приложением;
- не патчим Saby и не подменяем его native-библиотеки;
- не считаем OperationID успехом;
- не используем водителя для последовательных инженерных проб;
- не масштабируем старый FIX2 до 50 документов.

## Следующая инженерная задача

Собрать server-side adapter API ЕПГУ как отдельный модуль за интерфейсом и сначала прогнать его на синтетическом контракте. Реальный transport включается только после получения тестовых реквизитов и подтверждения официального профиля `60025907`.
